# Formology

**문서가 곧 도메인 모델이다.**

---

## 불행한 역사

헬스클럽에 가입한다고 상상해보세요.

1990년대, 컴퓨터 이전:

```
┌──────────────────────────────┐
│      ★ 회원등록카드 ★        │
├──────────────────────────────┤
│ 이름:    홍길동               │
│ 연락처:  010-1234-5678       │
│ 시작일:  1995-03-15          │
│ 기간:    6개월                │
│ 종류:    [ ] 일반  [✓] 프리미엄│
│ 담당 트레이너: 김코치         │
├──────────────────────────────┤
│ 서명: ___________            │
└──────────────────────────────┘
```

이 카드는 **관계**를 담고 있습니다. "홍길동은 이 클럽의 프리미엄 회원이고, 김코치가 담당한다." 카드를 보면 누구나 즉시 이해합니다.

그리고 IT 전문가가 왔습니다.

```
[사용자 등록]

아이디: ________
비밀번호: ________
비밀번호 확인: ________
이메일: ________

[등록]
```

**회원**이 **사용자**가 되었습니다. **등록카드**가 **등록 폼**이 되었습니다. **프리미엄 회원, 담당 코치**는 어디론가 사라졌습니다. IT 전문가는 "회원"을 `User` 테이블로, "등록카드"를 `CREATE` 연산으로, "프리미엄"을 `role` 컬럼 값으로 환원했습니다.

이것은 어디에서나 일어났습니다:

```
의사의 처방전         → "약품 주문" 화면
은행의 대출신청서     → "대출 상품 조회" 메뉴
식당의 주문전표       → "장바구니 → 결제"
학교의 성적표         → "학생 정보 시스템 > 성적 조회"
```

50년간 IT 전문가들은 모든 비즈니스를 Entity와 CRUD로 번역해왔습니다. 그 번역 과정에서 **목적, 맥락, 관계, 흐름** — 비즈니스의 본질 — 이 소실되었습니다.

## 두 번째 물결

1976년, Entity-Relationship 모델이 등장했습니다. 이후 반세기 동안 현업은 프로그래머의 언어에 적응해야 했습니다. 그것이 첫 번째 물결이었습니다.

지금, 두 번째 물결이 오고 있습니다.

AI 시대가 열리면서 "지식 그래프", "온톨로지", "시맨틱 웹"이 다시 부상합니다. 새로운 플랫폼들이 제안합니다: **"먼저 온톨로지를 설계하세요."**

이것은 1976년에 "먼저 Entity를 정의하세요"라고 했던 것과 **정확히 같은 구조의 실수**입니다:

```
1976년: "먼저 Entity를 정의하세요"     → 현업이 이해 못 함 → 개발자가 독단적으로 결정
2020년: "먼저 온톨로지를 설계하세요"   → 현업이 이해 못 함 → AI 엔지니어가 독단적으로 결정
```

추상화의 수준만 한 단계 올라갔을 뿐, 근본적 오류는 동일합니다: **인간에게 인간의 레이어가 아닌 곳에서 일하라고 요구하는 것.**

오해를 피하기 위해 미리 적습니다 — 틀린 것은 온톨로지가 아니라 **"먼저"**입니다. 온톨로지를 모두에게 **전제 조건**으로 요구하는 것. 그 이유는 [왜 서식인가](#왜-서식인가)에 있습니다.

> 상향식 온톨로지 방법론이 없다는 말이 아닙니다. 있습니다. 다만 전부 **온톨로지 엔지니어를 필수 주체로 전제**합니다 — [선행 연구와의 관계](docs/philosophy.md#선행-연구와의-관계).

## 세 개의 레이어

Formology는 이 문제에 대한 명확한 답을 가지고 있습니다.

```
┌─────────────────────────────────────────┐
│  인간의 레이어: 문서                      │
│                                          │
│  인간은 문서를 쓴다.                      │
│  회원등록카드, 검사의뢰서, 처방전.         │
│  수천 년간 해온 일이다.                   │
│  여기에 Entity도 Concept도 필요 없다.     │
└──────────────────┬──────────────────────┘
                   │ 시스템이 자동으로 도출
                   ▼
┌─────────────────────────────────────────┐
│  시스템의 레이어: 데이터                   │
│                                          │
│  문서의 구조에서 테이블이 도출된다.        │
│  문서의 필드에서 컬럼이 도출된다.          │
│  문서의 참조에서 관계가 도출된다.          │
└──────────────────┬──────────────────────┘
                   │ AI가 백그라운드에서 생성
                   ▼
┌─────────────────────────────────────────┐
│  지능의 레이어: 온톨로지                   │
│                                          │
│  AI가 스키마와 데이터 패턴을 분석한다.     │
│  이 모든 것에서 온톨로지가 자라난다.       │
│  인간은 이 과정을 볼 필요조차 없다.        │
└─────────────────────────────────────────┘
```

**인간은 문서를 쓰라. 시스템은 데이터를 관리하라. AI는 온톨로지를 만들어라.**

각자의 레이어에서, 각자가 잘하는 일을.

## 왜 서식인가

먼저 분명히 해 둡니다. **우리는 온톨로지를 부정하지 않습니다.**

현장에 도메인 전문가와 온톨로지 전문가가 함께 있다면, 온톨로지부터 시작하십시오. **그게 더 나을 수 있습니다.** 클래스와 공리를 제대로 세울 사람이 있는데 굳이 돌아갈 이유가 없습니다. 우리 주장은 그 전문가가 *쓸모없다*는 것이 아니라 *없어도 된다*는 것입니다. 필수 조건이 아니라는 뜻이지, 있으면 손해라는 뜻이 아닙니다.

문제는 그런 자리가 드물다는 것입니다. 대부분의 프로젝트에는 온톨로지 전문가가 없고 앞으로도 없습니다. 그때 실제로 벌어지는 일은 온톨로지 설계가 아니라 — **개발자가 혼자 테이블을 그리는 것**입니다. 그리고 위에서 본 반세기가 또 반복됩니다.

**Formology는 온톨로지의 대안이 아니라, 온톨로지의 실천 가능한 방법론입니다.**

온톨로지는 클래스, 객체, 속성, 액션, 관계, 제약, 공리를 요구합니다. 정당한 요구입니다.

여기서 오해가 하나 생깁니다. **Entity-CRUD가 이것들을 저장하지 못하는 게 아닙니다.** 전부 저장할 수 있습니다. 테이블도 있고 컬럼도 있고 FK도 있고 `status`도 있습니다. 문제는 다른 데 있습니다.

> **저장은 되는데, 저장한 뒤에 구별이 안 됩니다.**

업무가 서로 다르다고 여기는 것들이 스키마에서 **한 덩어리로 뭉개집니다.** 손실은 표현 수단의 부재가 아니라 **구별의 소실**입니다.

| 온톨로지가 요구하는 것 | Entity-CRUD에서 무엇이 뭉개지는가 | 서식·흐름은 무엇으로 구별하는가 |
|---|---|---|
| **클래스** | 서로 다른 서식이 `type` 컬럼 하나로 병합된다. 클래스 경계를 업무가 아니라 **저장 편의**가 정한다 | 서식 이름이 곧 경계. 현업이 다른 서식이라고 하면 다른 것이다 |
| **속성** | 본질적·부가적·설명적이 전부 같은 컬럼으로 평탄화. `NOT NULL`은 "빈 값 금지"일 뿐 **"이것이 본질"이 아니다** | 요소 삼분론 — *"이것 없이 여전히 이 서식인가?"* |
| **액션** | 의뢰·지시·보고·확인이 **전부 `INSERT`**. 네 개의 서로 다른 발화 행위가 한 연산으로 붕괴 | 접미어가 행위를 이름에 새긴다 — 서/지/표/록 |
| **관계** | FK는 "지금 참"만 표현한다. "그때 참"은 값을 복사할 수밖에 없는데, **스키마만 보고는 스냅샷인지 비정규화인지 실수인지 구별할 수 없다** | 참조 / 붙임 / 스냅샷 |
| **제약** | 같은 규칙이 DB·서버·화면 세 곳에 흩어지고 서로 어긋난다. 규칙의 출처는 어디에도 없다 | 서식 한 장에 한 번. 칸이 곧 규칙의 자리 |
| **상태·전이** | `status`는 상태의 **목록**일 뿐이다. 전이 조건도, 취소의 이유도 남지 않는다 | 흐름 일곱 패턴. 무효화도 문서로 남는다 |
| **공리** | 없다 | 선행 조건 — *"이거 쓰기 전에 뭐가 있어야 하나"* |

관계 행이 이 표에서 가장 아픈 자리입니다. 실제 스키마를 보십시오.

```sql
CREATE TABLE work_logs (
  work_order_id UUID NOT NULL,          -- 지금 참? 그때 참?
  product_name  VARCHAR(100) NOT NULL,  -- 스냅샷? 비정규화? 실수?
  ...
```

`product_name`이 왜 여기 있는지 **스키마는 답하지 못합니다.** 성능 때문에 복사한 것인지, 그때 값을 굳혀야 해서인지, 조인이 귀찮아서인지 — 답은 주석이나 위키나 그걸 짠 개발자의 머릿속에 있습니다. 그 개발자가 퇴사하면 사라집니다.

[우리 문서에도 이 테이블이 실려 있습니다](docs/realization.md#24-document-관계--fk계층). `-- 스냅샷: 그 시점의 제품명 (frozen)`이라는 주석과 함께. **주석을 지우면 의미가 사라집니다.** 그게 요점입니다.

서식은 답합니다. **기재란과 붙임란은 다른 칸이니까요.**

> 그러니 정확히 말하면 이렇습니다. Entity-CRUD로도 됩니다 — **개발자가 그 구별을 스키마 밖 어딘가에 빠짐없이 적어두기만 한다면.** 적어둘 자리가 없으니 관례로 갑니다. 서식은 그 자리를 처음부터 갖고 있습니다.

마지막 행에는 단서가 붙습니다. 서식에서 나오는 공리는 **업무가 실제로 쓰는 공리**입니다. "모든 X는 Y가 아니다" 같은 전칭·부정 공리는 나오지 않습니다 — 업무가 그것을 다루지 않기 때문입니다. 이 경계는 [철학과 원칙 7장](docs/philosophy.md#서식에서-도출되지-않는-것)에 적어 두었습니다.

현업은 이 표의 오른쪽 열을 설계한 적이 없습니다. **그냥 써 왔습니다.** 수백 년 동안.

> 우리가 서식에 집중하는 이유는 서식이 온톨로지보다 우월해서가 아닙니다.
> **온톨로지 전문가가 없는 자리에서도 온톨로지에 도달하는, 실천 가능한 입구이기 때문입니다.**
